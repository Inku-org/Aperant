Data Flow Architecture

LinearSyncEngine — how data moves between Aperant and Linear

Inbound Flow (Linear → Aperant)

Polling Cycle — runs every 60s (configurable)
1. FETCH
Linear GraphQL API
→ Issues updated since lastSyncAt
→ Filter by team/project
→ Include comments, state, labels
→ Track updatedAt per issue

2. DIFF
Compare fetched issues vs local sync state:
→ New issue? → Auto-create task + spec dir
→ New comments? → Append to task context + notify UI
→ Issue deleted/cancelled? → Archive task, stop agents
→ Status changed? → Log it (Aperant is source of truth, no override)
→ Assignee/labels changed? → Update task metadata
3. APPLY
For each detected change:
→ Write to spec/context files
→ Update task_metadata.json
→ Emit events to renderer stores
→ Update local sync_state.json

4. DELETION HANDLING
Issue deleted or moved to "Cancelled":
→ Set task status to cancelled
→ Kill running agents for that task
→ Post final status to Linear (if still exists)
→ Mark as archived in sync state

Outbound Flow (Aperant → Linear)

Event Queue — batched, fires on event or on poll cycle
EVENTS CAPTURED
Status changes → Update Linear issue state
Agent progress → Comment: "🤖 Planner started subtask 3/5"
PR/branch created → Comment with link
QA results → Comment: pass/fail + findings
Spec/plan ready → Comment with summary
Agent errors → Comment with error context
Task created in Aperant → Create Linear issue
QUEUE BEHAVIOR
→ Events queued in memory + persisted to disk
→ Batch flush: group comments per issue
→ Deduplicate: don't post same status twice
→ Retry with backoff on API failures
→ Rate limit aware (Linear: 1500 req/hr)
→ Survives app restart (read pending from disk)

COMMENT FORMAT
All agent comments prefixed with
[Aperant] so they're identifiable
and can be filtered by the poller
(avoids echo loops)
