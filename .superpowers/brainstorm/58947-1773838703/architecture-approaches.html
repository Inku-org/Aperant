Linear Integration Architecture — 3 Approaches

Aperant as source of truth, full bidirectional sync

A

Sync Engine (Recommended)

A dedicated LinearSyncEngine service in the main process that owns all synchronization logic.

  • Poller: Runs on interval (configurable, default 60s). Fetches issues updated since last sync timestamp. Detects new issues, status changes, new comments, deletions.
  • Event Emitter: Aperant-side events (status change, agent activity, PR created, QA result) feed into a queue. The engine batches and pushes to Linear as comments/state updates.
  • Conflict Resolution: Aperant always wins on status/content. Linear wins on deletions/cancellations.
  • State Tracking: A local sync_state.json per project tracks last sync time, issue mapping, and pending outbound events.

Pros

  • Clean separation — all sync logic in one place
  • Testable — engine can be unit tested with mock API
  • Resilient — queue survives app restarts
  • Easy to add webhook support later

Cons

  • More upfront architecture work
  • New service to maintain
B

Extend Existing Handlers

Build on the current IPC handler structure — add polling and outbound sync as new handler modules alongside the existing ones.

  • New handler: poll-handlers.ts — setInterval-based polling, diff detection
  • New handler: outbound-handlers.ts — listen to agent events, push comments/status to Linear
  • Extended types: Add sync state to existing TaskMetadata
  • No new service: Everything stays in IPC handler pattern

Pros

  • Follows existing codebase patterns
  • Less new architecture to learn
  • Faster to build initially

Cons

  • Sync logic scattered across multiple handlers
  • Harder to test holistically
  • Event ordering harder to guarantee
  • Will likely need refactoring as complexity grows
C

Hybrid — Sync Engine + Handler Integration

Build the sync engine (Approach A) but wire it through the existing IPC handler pattern so the frontend communicates with it the same way it does everything else.

  • Core: LinearSyncEngine class with poller + outbound queue
  • Integration: Thin IPC handlers that delegate to the engine
  • Events: Engine emits events that existing stores can subscribe to
  • Webhook ready: Engine accepts events from either poller or webhook endpoint

Pros

  • Clean engine + familiar IPC patterns
  • Frontend doesn't need to know about sync internals
  • Best testability
  • Natural webhook upgrade path

Cons

  • Most code to write initially
  • Slightly more abstraction layers

My Recommendation: Approach A (Sync Engine)

Given the scope — auto-import, bidirectional comments, full activity stream, deletion handling — this is too much logic to scatter across handlers. A dedicated engine keeps it maintainable and testable. Approach C adds unnecessary indirection since the IPC handlers are already thin wrappers.
